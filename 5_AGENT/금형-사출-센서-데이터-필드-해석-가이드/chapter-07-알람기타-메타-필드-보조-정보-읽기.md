# 7. 알람·기타 메타 필드 — 보조 정보 읽기

## 보조 필드의 역할: 데이터 필터링의 기준점

금형 사출 데이터셋에서 온도(T), 압력(P), 시간(ProcessTime)과 같은 물리적 측정값들이 '현상의 기록'이라면, 보조 필드들은 그 기록이 유효한지를 판단하는 '검증의 기준'이 됩니다. 특히 `Alarms` 필드는 단순한 상태 표시를 넘어, 분석가가 수집된 방대한 데이터 중 어떤 데이터를 분석 대상에 포함하고 어떤 데이터를 제외할지를 결정하는 1차 필터링의 핵심 지표로 작동합니다. 물리적 센서 값들이 정상 범위를 벗어났을 때, 그것이 공정의 특성 때문인지 아니면 설비의 이상으로 인한 노이즈인지를 구분하는 첫 번째 단서가 바로 이 필드에 담겨 있기 때문입니다.

`Alarms` 필드는 이진법(Binary) 형태로 기록되며, 값은 `1`과 `0`으로 구분됩니다. 자료에 근거하여 `1`은 True(알람 발생), `0`은 False(알람 미발생)를 의미합니다. 이는 매우 단순한 구조처럼 보이지만, 데이터 분석의 관점에서는 '정상성(Normality)'을 정의하는 결정적인 기준이 됩니다. 예를 들어, 특정 샷(Shot)의 온도 값이 비정상적으로 높게 측정되었을 때, `Alarms` 값이 `0`이라면 이는 공정 조건의 변화로 인한 물리적 현상으로 해석할 수 있지만, `Alarms` 값이 `1`이라면 설비 오류로 인한 잘못된 측정치일 가능성이 큽니다.

따라서 분석가는 본격적인 통계 분석이나 모델링에 앞서 데이터 정제(Cleaning) 단계에서 `Alarms` 필드를 최우선으로 활용해야 합니다. 일반적으로 '정상 공정'의 특성을 파악하고자 할 때는 `Alarms=0`인 데이터만을 추출하여 분석 집단을 구성하는 것이 안전합니다. 반면, 불량의 원인을 분석하거나 설비의 이상 징후를 탐색하고자 할 때는 `Alarms=1`인 구간을 집중적으로 살펴봄으로써, 알람 발생 시점의 센서 데이터(T, P)가 어떻게 변동했는지를 추적하는 방식으로 접근해야 합니다.

결과적으로 `Alarms` 필드는 데이터의 신뢰도를 보증하는 안전장치와 같습니다. 이 필드를 무시하고 전체 데이터를 평균 내거나 분석할 경우, 설비 오류로 인해 발생한 극단값(Outlier)이 전체 통계치를 왜곡하여 잘못된 결론에 도달할 위험이 있습니다. 따라서 분석가는 이 필드를 통해 데이터셋을 '정상군'과 '이상군'으로 명확히 분리하는 전처리 과정을 반드시 거쳐야 하며, 이를 통해 분석의 객관성을 확보할 수 있습니다.

| 필드명 | 값의 의미 | 해석 및 활용 |
| :--- | :--- | :--- |
| **Alarms** | 0: False / 1: True | 0은 정상 가동, 1은 설비 알람 발생 상태를 의미함 |

**그래서 이 필드가 뜻하는 바는:** 해당 샷(Shot)이 생산되는 과정에서 설비상에 알람이 발생했는지를 알려주는 지표이며, 데이터 분석 전 '정상 데이터'를 걸러내기 위한 필터로 사용됩니다.

## 식별용 보조 필드: Label의 의미와 한계

데이터셋에는 `Cycle` 외에도 `Label`이라는 필드가 존재합니다. 많은 분석 입문자가 이 필드에 어떤 물리적 의미나 공정상의 암호가 담겨 있을 것이라고 기대하지만, 자료에 따르면 `Label`은 단순한 일련번호(Serial Number)에 불과합니다. 이는 특정 물리량의 측정값이 아니며, 공정의 상태를 대변하는 지표도 아닙니다. 즉, `Label` 필드는 데이터의 '내용'이 아니라 데이터의 '순서'와 '개별성'을 보장하기 위한 관리용 식별자라고 해석해야 합니다.

분석가가 `Label` 필드를 활용해야 하는 주된 이유는 데이터의 개별 샷을 유일하게 식별(Unique Identification)하기 위해서입니다. 금형 사출 공정에서는 동일한 모델, 동일한 조건에서 수많은 샷이 반복적으로 생산됩니다. 이때 `Cycle` 번호는 배치(Batch)나 작업 단위에 따라 초기화될 가능성이 있는 반면, `Label`과 같은 일련번호는 전체 데이터셋 내에서 각 행을 구분 짓는 절대적인 주소 역할을 합니다. 따라서 데이터를 정렬하거나, 특정 시점의 샷을 추적하여 다른 테이블과 조인(Join)할 때 이 필드가 기준점이 됩니다.

하지만 주의해야 할 점은 `Label` 필드 자체에는 어떠한 분석적 가치도 없다는 것입니다. 예를 들어, `Label` 수치가 커진다고 해서 제품의 품질이 변하거나 공정 시간이 길어지는 등의 상관관계는 존재하지 않습니다. 이는 단순히 데이터베이스에 저장된 순서대로 부여된 번호일 가능성이 높기 때문입니다. 따라서 이 필드를 독립 변수로 설정하여 회귀 분석을 수행하거나 통계적 유의성을 찾으려는 시도는 무의미하며, 오직 '데이터 관리 및 추적'의 용도로만 한정하여 사용해야 합니다.

결론적으로 `Label` 필드는 분석의 대상이 아니라 분석을 위한 '인덱스(Index)'입니다. 분석가는 이 필드를 통해 데이터의 누락 여부를 확인하거나, 특정 이벤트가 발생한 샷의 위치를 정확히 짚어낼 수 있습니다. 물리적 의미가 없는 필드임을 명확히 인지함으로써, 불필요한 변수 탐색에 시간을 낭비하지 않고 실제 공정 데이터(T, P, ProcessTime)에 집중하는 것이 효율적인 분석 방향입니다.

| 필드명 | 의미 | 용도 |
| :--- | :--- | :--- |
| **Label** | 단순 일련번호 | 데이터 행의 개별 식별 및 순서 확인용 |

**그래서 이 필드가 뜻하는 바는:** 물리적 의미가 없는 단순한 순번 데이터이며, 각 샷을 고유하게 식별하기 위한 ID 역할만 수행합니다.

## 설명 미제공 필드: 데이터 공백의 명시적 처리

데이터셋에는 필드명은 존재하지만, 제공된 설명 자료에서 그 의미가 명시되지 않은 필드들이 다수 포함되어 있습니다. 구체적으로 `Weight1`, `Weight2`, `Quality`, `Worker`, `Part No(Injection Machine)` 필드가 이에 해당합니다. 분석가로서 가장 경계해야 할 지점은 바로 이 지점입니다. 도메인 지식을 바탕으로 'Weight는 제품의 무게일 것이다' 혹은 'Quality는 합격/불합격 여부일 것이다'라고 임의로 추측하여 해석하는 것은 데이터 분석에서 가장 위험한 접근 방식입니다.

현장 데이터는 기록하는 사람이나 설비 설정에 따라 필드명을 유연하게 사용하기 때문입니다. 예를 들어 `Weight`라는 필드가 실제 제품의 무게(g)가 아니라, 사출 시 투입된 레진의 설정 무게이거나, 혹은 특정 공정의 가중치(Weighting factor)를 의미할 수도 있습니다. 또한 `Quality` 필드가 단순한 합불 판정이 아니라, 품질 등급(A, B, C)이나 검사 항목의 코드를 의미할 수도 있습니다. 명확한 정의 없이 추측으로 내린 결론을 바탕으로 분석을 진행할 경우, 전체 분석 결과의 신뢰성이 무너지는 치명적인 오류를 범하게 됩니다.

따라서 본 가이드에서는 위에서 언급한 다섯 가지 필드(`Weight1`, `Weight2`, `Quality`, `Worker`, `Part No(Injection Machine)`)를 **'설명 미제공'** 상태로 명시합니다. 이는 해당 데이터가 중요하지 않다는 뜻이 아니라, 현재 주어진 근거 자료만으로는 이 필드들이 무엇을 측정하고 어떤 단위로 기록되었는지 확정할 수 없음을 의미합니다. 데이터 해석의 객관성을 유지하기 위해서는 '모르는 것을 모른다고 정의하는 것'이 분석의 기본 원칙입니다.

분석가는 설명이 없는 필드들을 다룰 때 다음과 같은 원칙을 지켜야 합니다. 첫째, 해당 필드들을 이용해 가설을 세우거나 결론을 도출하지 않습니다. 둘째, 만약 해당 필드들의 의미가 반드시 필요하다면, 임의로 해석하지 말고 반드시 데이터 생성 주체(설비 담당자 또는 공정 설계자)에게 재확인 절차를 거쳐야 합니다. 셋째, 확정된 정의가 내려지기 전까지는 분석 모델의 변수에서 제외하거나, 단순 참고용으로만 분류하여 해석의 리스크를 최소화해야 합니다.

| 필드명 | 설명 상태 | 처리 지침 |
| :--- | :--- | :--- |
| **Weight1** | 설명 미제공 | 임의 추측 금지, 분석 제외 또는 재확인 필요 |
| **Weight2** | 설명 미제공 | 임의 추측 금지, 분석 제외 또는 재확인 필요 |
| **Quality** | 설명 미제공 | 임의 추측 금지, 분석 제외 또는 재확인 필요 |
| **Worker** | 설명 미제공 | 임의 추측 금지, 분석 제외 또는 재확인 필요 |
| **Part No(Injection Machine)** | 설명 미제공 | 임의 추측 금지, 분석 제외 또는 재확인 필요 |

**그래서 이 필드들이 뜻하는 바는:** 현재 제공된 자료상으로는 측정 대상과 단위, 시점이 정의되지 않은 필드들이며, 근거 없는 추측으로 해석해서는 안 되는 영역입니다.

## 보조 필드 해석 시 주의사항: 데이터의 완전성 확인

마지막으로, 보조 필드들을 개별적으로 해석하는 것에 그치지 않고, 이를 주 공정 데이터(온도, 압력, 시간)와 어떻게 결합하여 바라봐야 하는지에 대한 관점이 필요합니다. 보조 필드는 그 자체로 결론을 내는 도구가 아니라, 주 공정 데이터의 맥락(Context)을 완성하는 퍼즐 조각입니다. 보조 필드와 주 공정 데이터 간의 상관관계를 해석할 때는 항상 '인과관계'와 '상관관계'를 구분하여 주의 깊게 접근해야 합니다.

예를 들어, `Alarms` 필드가 `1`인 구간에서 특정 온도 센서(`T1_Max`)의 값이 급증했다면, 이를 "온도가 높아서 알람이 발생했다"라고 단정하기 전에 "설비 알람으로 인해 제어 시스템이 오작동하여 온도가 튀었을 가능성"과 "온도 과승으로 인해 시스템이 알람을 발생시켰을 가능성"을 모두 열어두어야 합니다. 즉, 보조 필드는 현상의 결과일 수도 있고 원인일 수도 있습니다. 이러한 맥락을 파악하기 위해서는 `StartTime`과 `EndTime` 사이의 시간 흐름 속에서 보조 필드의 변화가 언제 일어났는지를 함께 살펴야 합니다.

또한, 데이터셋의 '완전성'을 확인하는 관점에서 보조 필드를 활용하십시오. 만약 `Label`이나 `Cycle` 번호가 중간에 끊겨 있거나, `Alarms` 필드에 빈 값(Null)이 다수 존재한다면, 이는 센서 데이터(T, P) 역시 일부 유실되었을 가능성이 매우 높음을 시사합니다. 즉, 보조 필드의 정합성이 깨진 데이터는 주 공정 데이터의 신뢰도 또한 낮을 확률이 크므로, 분석 전 데이터의 연속성과 완전성을 체크하는 지표로 삼아야 합니다.

결론적으로, 보조 필드는 주 데이터의 해석 방향을 잡아주는 가이드라인입니다. `Alarms`로 노이즈를 제거하고, `Label`로 개별 샷을 추적하며, 설명이 없는 필드를 배제함으로써 분석의 범위를 명확히 확정 짓는 과정이 선행되어야 합니다. 이렇게 정제된 환경 위에서 온도와 압력, 시간 데이터를 분석할 때 비로소 데이터가 가진 물리적 의미가 왜곡 없이 드러나게 됩니다.

**핵심 정리**
* **Alarms 필드는 분석의 1차 필터이다:** `1(True)`은 이상 상태, `0(False)`은 정상 상태를 의미하며, 분석 전 데이터 정제(Cleaning) 단계에서 정상군을 추출하는 기준으로 활용한다.
* **Label은 단순한 ID이다:** 물리적 의미가 없는 일련번호이므로, 분석 변수로 사용하지 말고 오직 샷의 개별 식별 및 추적 용도로만 사용한다.
* **미정의 필드는 추측하지 않는다:** `Weight`, `Quality`, `Worker` 등 설명이 없는 필드는 '설명 미제공'으로 명시하며, 도메인 지식을 이용한 임의 해석을 엄격히 배제하여 리스크를 최소화한다.
