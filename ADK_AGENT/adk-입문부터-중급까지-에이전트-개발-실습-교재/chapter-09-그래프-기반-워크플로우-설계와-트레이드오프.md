# 9. 그래프 기반 워크플로우 설계와 트레이드오프

## 9. 그래프 기반 워크플로우 설계와 트레이드오프

지금까지 우리는 에이전트를 순차적으로 연결하거나(Sequential), 병렬로 배치(Parallel)하는 방법을 배웠습니다. 하지만 실제 엔터프라이즈 환경의 비즈니스 프로세스는 훨씬 복잡합니다. 특정 조건에 따라 단계가 건너뛰어지기도 하고, 결과가 만족스럽지 않으면 이전 단계로 돌아가 재작업을 해야 하는 '루프(Loop)'가 발생하기도 합니다. ADK 2.0은 이를 해결하기 위해 '그래프 기반 아키텍처'를 도입했습니다.

### 9.1 지하철 노선도와 그래프 아키텍처

**쉬운 비유: 지하철 노선도**
우리가 지하철을 탈 때, 어떤 구간은 정해진 역을 순서대로 거쳐 가지만(결정론적 경로), 어떤 경우에는 목적지에 따라 환승역에서 다른 노선으로 갈아타거나(적응형 경로), 잘못 내렸을 때 다시 이전 역으로 돌아가기도 합니다. 

ADK 2.0의 그래프 아키텍처는 에이전트의 작업 흐름을 이 지하철 노선도처럼 설계하는 것입니다. 단순히 "A 다음에 B를 해"가 아니라, "현재 상태가 X라면 C로 가고, Y라면 다시 A로 돌아가라"는 정교한 제어가 가능해집니다.

**ADK 개념 및 용어**
* **그래프 기반 아키텍처 (Graph-based Architecture):** 작업 단위를 노드(Node)로, 작업의 흐름을 엣지(Edge)로 정의하여 전체 워크플로우를 관리하는 구조입니다.
* **노드 (Node):** 실제 작업이 수행되는 지점입니다. 여기에는 특정 역할을 가진 '에이전트'가 배치될 수도 있고, 단순한 '파이썬 함수'가 배치될 수도 있습니다.
* **엣지 (Edge):** 노드와 노드를 잇는 경로입니다.
* **결정론적 경로 (Deterministic Path):** 조건 없이 혹은 단순한 if-else 조건에 따라 정해진 순서대로 이동하는 경로입니다. 예측 가능성이 매우 높습니다.
* **적응형 경로 (Adaptive Path):** LLM의 추론 결과에 따라 다음에 어떤 노드로 이동할지 실시간으로 결정하는 경로입니다. 유연성이 높습니다.

**왜/언제 사용하는가?**
단순한 체인(Chain) 구조는 단계가 많아질수록 제어가 어렵고, 중간에 오류가 발생했을 때 전체를 다시 실행해야 하는 비효율이 있습니다. 그래프 아키텍처는 다음과 같은 상황에서 필수적입니다.
1. **복잡한 승인 절차:** "검토자 에이전트가 '반려'를 결정하면 다시 작성자 에이전트로 돌아가야 할 때"
2. **조건부 분기:** "사용자의 질문이 '결제' 관련이면 결제 에이전트로, '기술문의'면 기술지원 에이전트로 보낼 때"
3. **반복적 최적화:** "결과물의 품질이 기준치에 도달할 때까지 계속해서 수정 루프를 돌려야 할 때"

### 9.2 [실습] 그래프 기반의 '기술 문서 작성 및 검수' 워크플로우

이번 실습에서는 [초안 작성 → 기술 검토 → (반려 시) 초안 수정 → 최종 승인]으로 이어지는 그래프 워크플로우를 구현합니다.

#### 1. `tools.py` : 외부 도구 정의
에이전트가 사용할 간단한 검색 도구를 정의합니다.

```python
# tools.py
def technical_search(query: str):
    """기술적인 세부 사항을 검색하는 도구입니다."""
    # 실제로는 API 호출이 들어가지만, 실습을 위해 모의 데이터를 반환합니다.
    knowledge_base = {
        "ADK 2.0": "ADK 2.0은 그래프 기반 아키텍처를 통해 결정론적 코드와 AI 추론을 결합한 프레임워크입니다.",
        "Graph Architecture": "노드와 엣지를 통해 워크플로우를 정의하며 루프와 조건부 분기를 지원합니다."
    }
    return knowledge_base.get(query, "관련 정보를 찾을 수 없습니다.")
```

#### 2. `agent.py` : 역할별 에이전트 정의
작성자, 검토자, 승인자 세 가지 역할을 정의합니다.

```python
# agent.py
from adk import Agent # 가상의 ADK 라이브러리

# 1. 초안 작성 에이전트
writer = Agent(
    name="Writer",
    instruction="제공된 주제에 대해 전문적인 기술 초안을 작성하세요. 간결하고 명확하게 작성해야 합니다."
)

# 2. 기술 검토 에이전트
reviewer = Agent(
    name="Reviewer",
    instruction="작성된 초안의 기술적 정확성을 검토하세요. '승인' 또는 '반려' 중 하나로 응답하고, 반려 시 수정 이유를 상세히 적으세요."
)

# 3. 최종 승인 에이전트
approver = Agent(
    name="Approver",
    instruction="최종 결과물이 기업 표준에 맞는지 확인하고 최종 확정 공문을 작성하세요."
)
```

#### 3. `main.py` : 그래프 워크플로우 설계 및 실행
결정론적 경로와 적응형 경로를 결합하여 흐름을 제어합니다.

```python
# main.py
from agent import writer, reviewer, approver
from tools import technical_search
from adk import Graph, Node, Edge

# 그래프 객체 생성
workflow = Graph()

# 노드 추가
workflow.add_node("write_step", writer)
workflow.add_node("review_step", reviewer)
workflow.add_node("approve_step", approver)

# 엣지 설정 (흐름 정의)
# 1. 시작 -> 작성 (결정론적)
workflow.add_edge("START", "write_step")

# 2. 작성 -> 검토 (결정론적)
workflow.add_edge("write_step", "review_step")

# 3. 검토 -> (결과에 따라) 작성 또는 승인 (적응형 경로)
def review_router(state):
    # reviewer의 출력 결과에 따라 다음 경로를 결정하는 로직
    last_message = state.get_last_message()
    if "반려" in last_message:
        return "write_step"  # 다시 작성으로 돌아감 (Loop)
    return "approve_step"    # 승인 단계로 진행

workflow.add_adaptive_edge("review_step", review_router)

# 4. 승인 -> 종료 (결정론적)
workflow.add_edge("approve_step", "END")

# 실행
if __name__ == "__main__":
    user_input = "ADK 2.0의 그래프 아키텍처에 대한 기술 블로그 초안을 작성해줘."
    final_result = workflow.run(user_input)
    print(f"최종 결과물:\n{final_result}")
```

### 9.3 설계 관점의 분석: 비용 vs 속도 vs 품질 (Trade-off)

그래프 아키텍처를 설계할 때 가장 중요한 것은 **'트레이드오프(Trade-off)'**를 이해하는 것입니다. 모든 것을 완벽하게 만들려 하면 서비스는 사용할 수 없을 정도로 느려지거나 비용이 폭증합니다.

#### 1. 품질 (Quality)을 높이려면 → 비용 ↑, 속도 ↓
* **전략:** '반복 루프(Reflection Loop)'를 추가합니다. 검토 에이전트가 승인할 때까지 계속해서 다시 쓰게 만드는 구조입니다.
* **결과:** 결과물의 완성도는 극대화되지만, LLM API 호출 횟수가 늘어나 비용이 증가하고 사용자가 결과를 받을 때까지 시간이 오래 걸립니다.

#### 2. 속도 (Speed)를 높이려면 → 품질 ↓
* **전략:** 루프를 제거하고 '단방향 파이프라인(Linear Pipeline)'으로 설계하거나, 병렬(Parallel) 노드를 배치하여 동시에 작업을 수행합니다.
* **결과:** 응답 시간은 획기적으로 줄어들지만, 중간 단계의 오류가 걸러지지 않고 최종 결과물에 그대로 반영될 위험이 큽니다.

#### 3. 비용 (Cost)을 낮추려면 → 품질 ↓, 속도 ↓ (경우에 따라)
* **전략:** '모델 믹스(Model Mix)' 전략을 사용합니다. 
    * 라우팅/단순 검토(Router/Reviewer) → 가볍고 저렴한 소형 모델(Small Model) 배치
    * 핵심 집필/최종 승인(Writer/Approver) → 고성능 대형 모델(Large Model) 배치
* **결과:** 전체 비용은 낮아지지만, 소형 모델의 판단 미스로 인해 불필요한 루프가 발생하거나 품질이 저하될 수 있습니다.

**[설계 가이드라인 요약 표]**

| 우선순위 | 권장 아키텍처 | 모델 전략 | 리스크 |
| :--- | :--- | :--- | :--- |
| **최고 품질** | 다단계 루프 + 검증 노드 | 전 단계 고성능 모델 | 높은 비용, 느린 응답 속도 |
| **최저 지연** | 단방향 흐름 + 병렬 처리 | 최적화된 소형 모델 | 낮은 정확도, 할루시네이션 |
| **비용 최적화** | 조건부 분기 → 필요시만 루프 | 모델 믹스 (SLM → LLM) | 라우팅 오류 가능성 |

### 9.4 핵심 정리
* **그래프 아키텍처**는 노드(작업)와 엣지(흐름)로 구성되며, 단순 체인보다 복잡한 비즈니스 로직을 구현하기에 적합합니다.
* **결정론적 경로**는 예측 가능성을 제공하고, **적응형 경로**는 AI의 유연한 판단을 가능하게 합니다.
* 엔터프라이즈 에이전트 설계자는 **품질, 속도, 비용**이라는 세 가지 요소 사이의 균형점을 찾아 최적의 그래프 구조를 설계해야 합니다.
* 특히 **모델 믹스 전략**을 통해 중요도가 낮은 노드에는 가벼운 모델을 배치함으로써 효율성을 극대화할 수 있습니다.

### [정답 및 설계 의도]

**A1.** 적응형(Adaptive), 결정론적(Deterministic)
* **설계 의도:** 그래프 아키텍처의 가장 핵심적인 두 경로의 개념 차이를 구분할 수 있는지 확인합니다.

**A2.** **위험 요소:** 무한 루프(Infinite Loop)의 가능성. 작성자와 검토자의 의견이 일치하지 않을 경우, 계속해서 `write_step`으로 돌아가 API 비용이 폭증하고 응답이 오지 않을 수 있습니다.
* **해결 방안:** 루프 횟수 제한(Max Iteration)을 설정하여, 특정 횟수 이상 반복되면 중단하거나 상위 에이전트에게 전달하는 로직이 필요합니다.
* **설계 의도:** 프로덕션 환경에서 가장 위험한 '무한 루프' 시나리오를 인지하고 방어 코드를 생각하게 합니다.

**A3.** **배치 위치:** 시작 노드(START)와 첫 번째 처리 노드 사이.
* **이유:** 요청의 성격(단순 vs 복잡)을 먼저 판단해야 이후의 경로(즉시 답변 vs 다단계 프로세스)를 결정할 수 있기 때문입니다. 이를 '라우팅(Routing)' 단계라고 합니다.
* **설계 의도:** 워크플로우의 진입점에서 적절한 분기점을 설정하는 설계 능력을 평가합니다.

**A4. 제안 예시:** "캐싱(Caching) 노드와 병렬 검증 구조 도입"
* **설명:** 자주 묻는 질문은 캐시 노드에서 즉시 처리(속도 ↑)하고, 복잡한 질문은 초안 작성과 동시에 가벼운 검증 모델이 병렬로 체크하여 이상 징후가 있을 때만 정밀 검토 단계로 진입하게 설계합니다.
* **설계 의도:** 비용, 속도, 품질의 트레이드오프를 실제 서비스 시나리오에 적용해 해결책을 도출할 수 있는지 확인합니다.

**A5. 가이드라인:**
* `state` 객체에 `retry_count` 필드를 추가합니다.
* `review_router` 내에서 `state.retry_count += 1`을 수행합니다.
* `if state.retry_count >= 3: return "admin_step"` 조건문을 추가하여 흐름을 제어합니다.
* **설계 의도:** 상태 관리(State Management) 개념을 익히고, 예외 상황을 처리하는 엔터프라이즈급 설계 패턴을 실습하게 합니다.
