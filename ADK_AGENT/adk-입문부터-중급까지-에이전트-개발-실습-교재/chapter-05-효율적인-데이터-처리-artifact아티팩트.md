# 5. 효율적인 데이터 처리: Artifact(아티팩트)

## 5. 효율적인 데이터 처리: Artifact(아티팩트)

지난 챕터에서 우리는 세션(Session)과 메모리(Memory)를 통해 에이전트가 대화의 흐름을 기억하는 방법을 배웠습니다. 하지만 실제 엔터프라이즈 환경에서는 수백 페이지의 문서, 거대한 JSON 로그, 혹은 수천 줄의 소스 코드를 다뤄야 하는 경우가 많습니다. 이 모든 데이터를 대화 기록(Context)에 그대로 집어넣으면 어떻게 될까요? 토큰 비용이 폭증하고, 모델은 정작 중요한 정보를 놓치는 '정보의 홍수' 상태에 빠지게 됩니다. 이번 챕터에서는 ADK의 핵심 최적화 기술인 **아티팩트(Artifact)**를 통해 대규모 데이터를 스마트하게 다루는 방법을 학습합니다.

---

## 5.1 쉬운 비유: 도서관 사서와 인덱스 카드

여러분이 도서관 사서에게 "최근 10년간의 AI 트렌드에 대해 알려줘"라고 요청했다고 가정해 봅시다.

*   **아티팩트가 없는 방식 (Prompt Stuffing):** 사서가 도서관에 있는 AI 관련 책 100권을 전부 책상 위에 펼쳐놓고, 그 모든 내용을 한꺼번에 읽어주려 하는 것과 같습니다. 책상이 꽉 차서 더 이상 아무것도 놓을 수 없고(컨텍스트 창 제한), 사서는 너무 많은 정보 때문에 핵심을 놓치게 됩니다.
*   **아티팩트를 사용하는 방식 (Artifact & Lazy-loading):** 사서는 책상 위에 **'책 목록(인덱스 카드)'**만 올려둡니다. 그리고 "여기에 관련 책 100권이 있습니다. 구체적으로 어떤 부분이 궁금하신가요?"라고 묻습니다. 여러분이 "3번 책의 50페이지 내용을 알려줘"라고 요청하는 순간, 사서는 그 책의 해당 페이지만 빠르게 찾아 읽어줍니다.

여기서 **'책 목록'**이 아티팩트의 참조(Reference)이며, 필요할 때만 실제 내용을 가져오는 행위가 바로 **지연 로딩(Lazy-loading)**입니다.

---

## 5.2 ADK 개념 및 용어

### 아티팩트 (Artifact)
아티팩트는 에이전트가 처리하는 **'구조화된 대규모 데이터 객체'**를 의미합니다. 단순한 문자열이 아니라, 고유 ID와 메타데이터를 가진 독립적인 개체로 관리됩니다. ADK는 이를 통해 데이터의 본문과 데이터의 존재(참조)를 분리하여 관리합니다.

### 지연 로딩 (Lazy-loading)
데이터 전체를 모델의 프롬프트에 즉시 주입하지 않고, **모델이 해당 데이터의 내용이 필요하다고 판단하여 요청하거나, 특정 조건이 충족되었을 때만** 실제 내용을 컨텍스트에 포함시키는 방식입니다.

### 토큰 최적화 (Token Optimization)
불필요한 이벤트 필터링과 아티팩트 참조 방식을 통해, 모델에 전달되는 토큰 수를 최소화하여 비용을 절감하고 응답 속도를 높이는 전략입니다.

---

## 5.3 왜, 언제 사용하는가? (당위성)

### 왜 사용하는가?
1.  **비용 절감:** LLM의 과금 체계는 토큰 단위입니다. 수만 토큰의 데이터를 매 턴마다 전송하는 것은 매우 비효율적입니다.
2.  **성능 향상 (Attention Focus):** 모델의 컨텍스트 윈도우가 크더라도, 입력값이 너무 길면 중간 내용을 망각하는 'Lost in the Middle' 현상이 발생합니다. 필요한 정보만 정밀하게 주입함으로써 답변의 정확도를 높일 수 있습니다.
3.  **시스템 안정성:** 토큰 제한(Context Window Limit)으로 인해 에이전트가 갑자기 멈추는 현상을 방지합니다.

### 언제 사용하는가?
*   **대용량 문서 분석:** PDF, HTML, 로그 파일 등 텍스트 양이 많은 데이터를 다룰 때.
*   **코드 베이스 탐색:** 수십 개의 파일로 구성된 프로젝트 코드를 분석할 때.
*   **구조화된 대량 데이터 처리:** 거대한 JSON/CSV 데이터를 기반으로 통계를 내거나 특정 값을 추출할 때.

## 5.4 단계별 Python 코드 실습

이제 실제로 대용량 데이터를 아티팩트로 처리하는 에이전트를 구현해 보겠습니다. 이번 실습에서는 '거대한 시스템 로그 파일'을 분석하는 시나리오를 설정합니다.

### 1. `tools.py`: 아티팩트를 생성하는 도구 정의
단순히 텍스트를 반환하는 것이 아니라, ADK의 아티팩트 구조로 데이터를 관리하는 도구를 만듭니다.

```python
# tools.py
import uuid

# 가상의 대규모 데이터 (실제로는 파일이나 DB에서 읽어옴)
LARGE_LOG_DATA = {
    "log_2023_01": "ERROR: Database connection failed at 10:00... " * 100,
    "log_2023_02": "INFO: User login successful at 11:00... " * 100,
    "log_2023_03": "CRITICAL: Memory leak detected at 12:00... " * 100,
}

def get_log_files():
    """사용 가능한 로그 파일 목록을 반환합니다."""
    return list(LARGE_LOG_DATA.keys())

def read_log_artifact(log_id: str):
    """
    특정 로그 ID의 내용을 가져옵니다. 
    실제 구현에서는 이 함수가 호출될 때만 데이터가 모델에 전달되는 
    Lazy-loading 구조를 가집니다.
    """
    if log_id not in LARGE_LOG_DATA:
        return f"Error: {log_id} 파일을 찾을 수 없습니다."
    
    # ADK 내부적으로는 이 반환값이 Artifact 객체로 래핑되어 관리됩니다.
    return {
        "artifact_id": log_id,
        "content": LARGE_LOG_DATA[log_id],
        "metadata": {"type": "system_log", "size": len(LARGE_LOG_DATA[log_id])}
    }
```

### 2. `agent.py`: 아티팩트 기반 에이전트 설계
에이전트에게 "먼저 목록을 확인하고, 필요한 파일만 요청하라"는 지침을 부여합니다.

```python
# agent.py
from adk import Agent # 가상의 ADK 라이브러리 임포트

class LogAnalyzerAgent(Agent):
    def __init__(self):
        super().__init__(
            name="LogAnalyzer",
            instruction=(
                "당신은 시스템 로그 분석 전문가입니다. "
                "1. 먼저 `get_log_files`를 통해 사용 가능한 로그 목록을 확인하세요. "
                "2. 모든 로그를 한꺼번에 읽으려 하지 마세요. "
                "3. 사용자의 질문과 가장 관련이 깊은 로그 파일만 `read_log_artifact`로 요청하여 분석하세요. "
                "4. 분석 결과만 요약해서 보고하세요."
            )
        )
```

### 3. `main.py`: 실행 및 토큰 효율성 확인

```python
# main.py
from agent import LogAnalyzerAgent
from tools import get_log_files, read_log_artifact
from adk import Runtime

def main():
    # 에이전트 및 도구 설정
    agent = LogAnalyzerAgent()
    agent.register_tool(get_log_files)
    agent.register_tool(read_log_artifact)
    
    runtime = Runtime()
    
    # 시나리오: 특정 시점의 에러를 찾는 질문
    user_query = "2023년 1월에 발생한 치명적인 에러가 무엇인지 알려줘."
    
    print(f"User: {user_query}")
    response = runtime.run(agent, user_query)
    print(f"Agent: {response}")

if __name__ == "__main__":
    main()
```

## 5.5 핵심 정리

| 개념 | 설명 | 핵심 가치 |
| :--- | :--- | :--- |
| **Artifact** | 대규모 데이터를 구조화하여 관리하는 객체 | 데이터-참조 분리 |
| **Lazy-loading** | 필요 시점에만 데이터를 로드하는 방식 | 토큰 낭비 방지 |
| **Token Optimization** | 필터링 및 요약을 통해 입력 토큰을 최소화함 | 비용 절감 및 속도 향상 |
| **동작 흐름** | 목록 확인 → 특정 아티팩트 선택 → 내용 로드 → 분석 | 효율적인 추론 경로 |

## [정답 및 설계 의도]

**정답 1:** 지연 로딩(Lazy-loading), 아티팩트(Artifact)
*   **설계 의도:** 챕터의 핵심 용어를 정확히 이해했는지 확인합니다.

**정답 2:** 
*   **문제점:** 모든 로그 내용을 하나의 문자열로 합쳐 한꺼번에 반환하므로, 로그 양이 많아질수록 프롬프트 토큰 제한을 초과(Overflow)하게 되며, 불필요한 데이터까지 모두 전송되어 비용이 급증합니다.
*   **개선안:** `get_log_files()`처럼 목록만 먼저 제공하는 도구와, 특정 ID를 입력받아 해당 내용만 반환하는 `read_log_artifact()` 도구로 분리해야 합니다.
*   **설계 의도:** Prompt Stuffing의 위험성을 인지하고 아티팩트의 필요성을 논리적으로 도출할 수 있는지 평가합니다.

**정답 3:** 
1.  **파일 목록 조회:** `list_files()` 도구로 전체 파일 경로/이름 목록(Artifact Reference)을 획득.
2.  **관련 파일 식별:** 모델이 질문과 관련된 파일(예: `auth.py`, `user_service.py`)을 선정.
3.  **부분 로딩:** `read_file_artifact(file_id)`를 통해 선정된 파일의 내용만 로드.
4.  **분석 및 답변:** 로드된 소스 코드를 바탕으로 답변 생성.
*   **설계 의도:** 실제 대규모 프로젝트 상황에 아티팩트 워크플로우를 적용하는 설계 능력을 배양합니다.

**정답 4:**
*   **Memory:** 주로 대화의 맥락, 사용자의 선호도, 이전 단계의 결과 등 '상태'를 저장하며, 대화 흐름에 따라 유동적으로 요약되어 전달됩니다.
*   **Artifact:** 외부의 거대한 '정적 데이터'를 저장하며, 모델이 명시적으로 요청하거나 특정 조건이 맞을 때만 '참조'를 통해 선택적으로 전달됩니다.
*   **설계 의도:** 컨텍스트 관리의 두 축인 메모리와 아티팩트의 역할 분담을 명확히 구분하게 합니다.

**정답 5:**
*   **제안:** 
    1. **청크 분할(Chunking):** 아티팩트 내용을 일정 길이로 나누어 페이지네이션(Pagination) 형태로 제공.
    2. **사전 요약(Pre-summarization):** 아티팩트를 로드하기 전, 도구 레벨에서 간단한 요약본을 먼저 제공하여 모델이 정말로 전체 내용이 필요한지 결정하게 함.
    3. **필터링(Filtering):** 정규표현식 등을 이용해 에러 키워드가 포함된 라인만 추출하여 전달.
*   **설계 의도:** 단일 아티팩트조차 너무 클 수 있는 엔터프라이즈급 상황에서의 심화 최적화 전략을 생각하게 합니다.
