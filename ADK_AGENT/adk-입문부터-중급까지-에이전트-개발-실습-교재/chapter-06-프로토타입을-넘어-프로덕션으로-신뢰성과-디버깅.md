# 6. 프로토타입을 넘어 프로덕션으로: 신뢰성과 디버깅

## 6.1 프로덕션 에이전트를 위한 비유: '홈쿡'과 '프로 셰프'의 차이

우리가 지금까지 만든 에이전트는 마치 '홈쿡'과 같습니다. 운이 좋으면 아주 맛있는 요리를 만들어내지만, 가끔은 간을 맞추지 못하거나 재료가 떨어졌을 때 당황해서 요리를 망치기도 합니다. 하지만 집에서 먹는 요리는 조금 짜더라도 웃으며 넘길 수 있죠.

반면, '프로덕션 에이전트'는 호텔의 '프로 셰프'가 되어야 합니다. 수백 명의 손님에게 동일한 품질의 요리를 제공해야 하며, 만약 재료가 신선하지 않다면 즉시 대체재를 찾거나 손님에게 정중히 알리는 '표준 운영 절차(SOP)'가 있어야 합니다. 또한, 요리가 잘못 나왔을 때 어느 단계에서 실수가 있었는지 정확히 추적(Tracing)하여 다음에는 같은 실수를 반복하지 않도록 기록해야 합니다.

프로토타입 에이전트가 "답변이 잘 나오네?"에 집중했다면, 프로덕션 에이전트는 **"언제, 왜 실패하며, 실패했을 때 어떻게 복구하는가?"**에 집중합니다.

## 6.2 ADK의 신뢰성 및 디버깅 핵심 개념

에이전트를 프로덕션 수준으로 끌어올리기 위해 ADK가 제공하는 핵심 개념들은 다음과 같습니다.

1. **오류 처리 및 복구 (Error Handling & Recovery)**: 도구(Tool) 호출 실패나 모델의 잘못된 응답이 발생했을 때, 시스템이 완전히 멈추지 않고 사용자에게 적절한 안내를 하거나 스스로 재시도하는 메커니즘입니다.
2. **관측 가능성 및 트레이싱 (Observability & Tracing)**: 에이전트가 내부적으로 어떤 추론 과정을 거쳐 도구를 선택했고, 도구로부터 어떤 값을 받아 최종 답변을 냈는지 모든 단계를 기록하는 것입니다.
3. **결정론적 경로 설계 (Deterministic Path Design)**: ADK 2.0의 그래프 기반 아키텍처를 활용하여, AI의 자율성에만 맡기지 않고 반드시 거쳐야 하는 필수 단계나 제약 조건을 설정함으로써 실행 경로의 예측 가능성을 높이는 것입니다.
4. **구조적 컨텍스트 필터링 (Structural Context Filtering)**: 불필요한 이벤트나 중복된 로그를 필터링하여 토큰 낭비를 줄이고, 에이전트가 현재 해결해야 할 문제에만 집중하게 만드는 최적화 기법입니다.

## 6.3 왜, 언제 신뢰성 설계가 필요한가?

### 왜 필요한가? (당위성)
LLM은 본질적으로 확률적(Probabilistic)입니다. 동일한 질문에도 매번 다른 답변을 할 수 있으며, 특히 외부 도구를 연동했을 때 다음과 같은 변수가 발생합니다.
- **API 장애**: 외부 서비스의 일시적 다운타임.
- **형식 오류**: 모델이 도구에 전달할 인자(Argument) 형식을 잘못 생성함.
- **환각(Hallucination)**: 도구가 에러를 반환했음에도 불구하고, 모델이 마치 성공한 것처럼 거짓 답변을 생성함.

### 언제 적용하는가? (적용 시점)
- 단순 데모 단계를 지나 **실제 사용자에게 배포**하기 직전.
- 에이전트의 **응답 품질이 들쑥날쑥**하여 일관성을 확보해야 할 때.
- 에러 발생 시 원인을 찾기 위해 **수많은 로그를 일일이 뒤지는 것이 불가능**해질 때.

## 6.4 [실습] 예측 가능한 에이전트 구현하기

이번 실습에서는 날씨 정보를 가져오는 에이전트를 구현합니다. 단순히 API를 호출하는 것이 아니라, **1) 잘못된 도시 이름 입력 시의 예외 처리**, **2) API 호출 실패 시의 복구 전략**, **3) 전체 실행 과정의 트레이싱**을 구현합니다.

### 1. `tools.py` - 견고한 도구 설계
도구 내부에서 예외를 처리하여 에이전트가 '에러 메시지'를 읽고 스스로 판단하게 만듭니다.

```python
# tools.py
import random

def get_weather(city: str):
    """특정 도시의 현재 날씨 정보를 가져옵니다."""
    print(f"[Tool Log] get_weather 호출됨: {city}")
    
    # 시뮬레이션: 잘못된 도시 이름 처리
    invalid_cities = ["unknown", "test", "123"]
    if city.lower() in invalid_cities:
        return {"error": f"'{city}'는 유효한 도시 이름이 아닙니다. 정확한 도시명을 입력해주세요."}

    # 시뮬레이션: 네트워크 일시적 오류 발생 (20% 확률)
    if random.random() < 0.2:
        return {"error": "날씨 서버와 연결하는 중 일시적인 네트워크 오류가 발생했습니다."}

    # 정상 응답
    weather_data = {"Seoul": "맑음, 25도", "New York": "비, 18도", "Tokyo": "흐림, 22도"}
    result = weather_data.get(city.capitalize(), "정보 없음")
    
    if result == "정보 없음":
        return {"error": f"'{city}'에 대한 날씨 데이터를 찾을 수 없습니다."}
        
    return {"status": "success", "data": result}
```

### 2. `agent.py` - 신뢰성 지시문 설계
에이전트에게 에러가 발생했을 때 어떻게 행동해야 하는지 구체적인 가이드라인을 제공합니다.

```python
# agent.py
from adk import Agent # 가상의 ADK 라이브러리

class WeatherAgent(Agent):
    def __init__(self, model):
        super().__init__(
            name="ReliableWeatherAgent",
            model=model,
            instruction=(
                "당신은 날씨 정보 제공 에이전트입니다. 도구 사용 시 다음 규칙을 엄격히 따르세요:\n"
                "1. 도구가 'error'를 반환하면, 절대로 거짓 정보를 지어내지 마세요.\n"
                "2. 네트워크 오류가 발생했다면, 사용자에게 잠시 후 다시 시도해달라고 정중히 요청하세요.\n"
                "3. 도시 이름이 잘못되었다면, 어떤 부분이 잘못되었는지 설명하고 다시 확인을 요청하세요.\n"
                "4. 모든 답변은 [상태: 성공/실패] 형식을 앞에 붙여 응답하세요."
            )
        )
```

### 3. `main.py` - 실행 및 디버깅 루프
에이전트의 사고 과정(Thought Process)을 추적하며 실행합니다.

```python
# main.py
from agent import WeatherAgent
from tools import get_weather
from adk import Runtime

def main():
    # 모델 설정 및 에이전트 초기화
    model = "gemini-1.5-pro" 
    agent = WeatherAgent(model=model)
    
    # 도구 연결
    agent.register_tool(get_weather)
    
    # 테스트 케이스: [정상, 잘못된 도시, 랜덤 에러 유도]
    test_queries = [
        "서울 날씨 알려줘", 
        "unknown 도시 날씨 알려줘", 
        "뉴욕 날씨 알려줘"
    ]
    
    runtime = Runtime()
    
    for i, query in enumerate(test_queries):
        print(f"\n--- Test Case {i+1}: {query} ---")
        
        # ADK의 트레이싱 모드 활성화 (내부 추론 과정 출력)
        with runtime.trace_session():
            response = runtime.run(agent, query)
            print(f"Final Response: {response}")

if __name__ == "__main__":
    main()
```

## 6.5 핵심 정리

- **프로덕션 에이전트**는 단순한 기능 구현을 넘어 **예외 상황에서의 일관된 동작**과 **추적 가능성**을 확보해야 한다.
- **도구 설계**: 도구가 단순하게 Crash되는 것이 아니라, 구조화된 에러 메시지(JSON 형태 등)를 반환하도록 설계하여 에이전트가 상황을 인지하게 해야 한다.
- **지시문(Instruction)**: 에러 상황에 대한 대응 시나리오를 지시문에 명시함으로써 모델의 환각을 방지하고 예측 가능한 응답을 유도한다.
- **트레이싱(Tracing)**: `runtime.trace_session()`과 같은 도구를 통해 에이전트의 [생각 → 도구 선택 → 결과 해석 → 답변] 과정을 투명하게 관찰해야 한다.

## [정답 및 설계 의도]

**A1.** 결정론적(Deterministic), 그래프(Graph)
- **의도**: ADK 2.0의 핵심인 결정론적 코드와 그래프 구조의 개념을 이해했는지 확인합니다.

**A2.** 
- **문제점**: `raise Exception`을 사용하면 프로그램 자체가 중단(Crash)되어 에이전트가 에러를 인지하고 복구할 기회를 잃게 됩니다.
- **수정**: `return {"error": "해당 사용자의 데이터를 찾을 수 없습니다."}`와 같이 구조화된 에러 메시지를 반환하여 에이전트가 이를 읽고 사용자에게 친절히 안내하도록 수정해야 합니다.
- **의도**: 예외 발생 시 프로그램 중단과 에러 메시지 반환의 차이를 이해하고, 에이전트에게 제어권을 넘겨주는 설계 방식을 익히게 합니다.

**A3.**
- **도구 측면**: API 응답 코드가 503일 때, 이를 캐치하여 `{"status": "server_error", "message": "Service Unavailable"}` 형태의 JSON을 반환하도록 구현합니다.
- **지시문 측면**: "도구로부터 `server_error`를 받으면, 사용자에게 현재 서버 점검 중임을 알리고 나중에 다시 시도해달라고 안내하라"는 지침을 추가합니다.
- **의도**: 도구의 출력과 에이전트의 지시문이 어떻게 상호작용하여 최종 사용자 경험(UX)을 만드는지 설계 능력을 평가합니다.

**A4.** 
- **답변**: 모든 로그를 기록하는 대신, 중요한 이벤트(도구 호출, 최종 응답)만 남기고 중간의 단순 반복 과정은 요약(Summarization)하거나 필터링하는 '구조적 컨텍스트 필터링'을 적용합니다.
- **의도**: 토큰 효율성과 관측 가능성 사이의 트레이드오프를 해결하는 ADK의 컨텍스트 관리 방식을 이해했는지 확인합니다.

**A5.**
- **설계**: `Start` → `Node 1: 결제 요청 분석` → `Node 2: 금액 검증(결정론적 코드)` → `Node 3: 사용자 승인 대기(인간 개입)` → `Node 4: 결제 API 실행` → `End`.
- **설명**: 각 단계를 노드로 정의하고, 특히 '사용자 승인' 단계를 필수 체크포인트로 설정하여 AI가 임의로 결제 단계를 건너뛰지 못하도록 경로를 고정합니다.
- **의도**: 고위험 작업에서 AI의 자율성을 제한하고 결정론적 경로를 설계하는 '에이전트 설계자'로서의 관점을 갖추었는지 평가합니다.
