# 7. 멀티 에이전트 기초: Sequential 및 Parallel 구조

## 7.1 오케스트라의 지휘자와 연주자: 멀티 에이전트의 비유

혼자서 모든 일을 다 하는 '슈퍼맨' 에이전트를 상상해 보세요. 그는 기획도 하고, 자료 조사도 하고, 글도 쓰고, 오타 교정까지 합니다. 처음에는 편리하겠지만, 작업이 복잡해질수록 슈퍼맨은 혼란에 빠집니다. 지시 사항(Instruction)이 너무 길어져 정작 중요한 내용을 놓치거나, 자료 조사 단계의 오류를 그대로 글쓰기에 반영하는 실수를 범하게 됩니다.

이때 필요한 것이 바로 **'멀티 에이전트(Multi-Agent)'** 구조입니다. 이는 한 명의 슈퍼맨 대신, 각 분야의 전문가들을 모아 팀을 꾸리는 것과 같습니다.

*   **순차적(Sequential) 구조**는 **'공장의 조립 라인'**과 같습니다. 원재료가 투입되면 [조사원 → 작성자 → 검토자] 순으로 작업물이 전달되며, 앞 단계의 결과물이 다음 단계의 입력값이 됩니다. 앞 사람이 일을 잘 마쳐야 뒷 사람이 일을 시작할 수 있는 구조입니다.
*   **병렬적(Parallel) 구조**는 **'태스크포스(TF) 팀의 분업'**과 같습니다. 하나의 큰 주제를 놓고 [시장 조사원], [기술 분석가], [경쟁사 분석가]가 동시에 각자의 영역을 조사합니다. 이후 팀장이 이 결과물들을 한데 모아 최종 보고서를 완성합니다.

---

## 7.2 ADK의 멀티 에이전트 개념 및 용어

ADK 2.0은 단순한 챗봇의 연결이 아니라, **그래프 기반 아키텍처(Graph-based Architecture)**를 통해 에이전트 간의 흐름을 제어합니다.

*   **오케스트레이션(Orchestration):** 여러 에이전트가 언제, 어떤 순서로 동작할지를 결정하고 제어하는 전체적인 설계 과정을 의미합니다.
*   **순차적 워크플로우(Sequential Workflow):** 에이전트 A의 출력이 에이전트 B의 입력으로 이어지는 선형적인 흐름입니다. 결정론적인 경로(Deterministic Path)를 가지므로 결과의 예측 가능성이 높습니다.
*   **병렬적 워크플로우(Parallel Workflow):** 동일한 입력에 대해 여러 에이전트가 동시에 서로 다른 작업을 수행하는 흐름입니다. 처리 시간을 단축할 수 있으며, 다양한 관점의 결과를 동시에 얻을 때 유리합니다.
*   **어그리게이터(Aggregator):** 병렬로 수행된 여러 에이전트의 결과물을 하나로 취합하고 요약하여 최종 결과물을 만드는 역할을 수행하는 에이전트나 로직을 말합니다.

## 7.3 왜 멀티 에이전트를 사용하는가? (당위성)

단일 에이전트로도 구현 가능해 보이지만, 엔터프라이즈급 프로덕션 환경에서 멀티 에이전트를 설계하는 이유는 명확합니다.

1.  **관심사의 분리(Separation of Concerns):** 각 에이전트에게 명확하고 좁은 범위의 역할(Role)만 부여함으로써, 프롬프트의 복잡도를 낮추고 추론의 정확도를 높일 수 있습니다.
2.  **토큰 효율성 및 컨텍스트 관리:** 모든 지시사항을 하나의 프롬프트에 넣으면 토큰 소모가 극심하고 모델이 지시사항을 누락할 확률이 높습니다. 필요한 단계에서 필요한 지시문만 전달함으로써 효율을 극대화합니다.
3.  **품질 검증 체계 구축:** '작성자'와 '검토자'를 분리함으로써, 스스로 자신의 오류를 찾지 못하는 LLM의 한계를 극복하고 상호 검증 프로세스를 강제할 수 있습니다.
4.  **확장성:** 새로운 기능이 필요할 때 전체 시스템을 수정하는 대신, 새로운 전문 에이전트를 추가하고 워크플로우에 연결하기만 하면 됩니다.

## 7.4 단계별 Python 코드 실습

이번 실습에서는 **'시장 분석 보고서 생성기'**를 만들어 봅니다. 
- **순차적 구조:** [자료 조사 → 보고서 작성]
- **병렬적 구조:** [트렌드 분석, 경쟁사 분석] → [최종 취합]

### 1. `tools.py` : 에이전트가 사용할 도구 정의
```python
# tools.py
def fetch_market_data(topic: str):
    """특정 주제에 대한 시장 데이터를 가져오는 가상 도구"""
    print(f"[Tool] {topic}에 대한 데이터를 검색 중...")
    return f"{topic} 시장은 현재 연평균 15% 성장 중이며, AI 도입률이 급증하고 있습니다."

def fetch_competitor_data(topic: str):
    """경쟁사 정보를 가져오는 가상 도구"""
    print(f"[Tool] {topic} 경쟁사 데이터를 검색 중...")
    return f"{topic} 분야의 주요 경쟁사는 A사(점유율 30%)와 B사(점유율 20%)입니다."

def check_grammar(text: str):
    """텍스트의 문법을 교정하는 가상 도구"""
    print("[Tool] 문법 및 톤앤매너 교정 중...")
    return f"[교정 완료] {text}"
```

### 2. `agent.py` : 전문 에이전트 클래스 정의
```python
# agent.py
from adk import Agent # ADK 프레임워크 가정

class ResearcherAgent(Agent):
    def __init__(self):
        super().__init__(
            name="Researcher",
            instruction="당신은 전문 시장 조사원입니다. 제공된 도구를 사용하여 정확한 수치와 팩트 중심의 데이터를 수집하세요.",
            model="gemini-1.5-flash"
        )

class WriterAgent(Agent):
    def __init__(self):
        super().__init__(
            name="Writer",
            instruction="당신은 비즈니스 라이터입니다. 조사원의 데이터를 바탕으로 전문적인 보고서 형식으로 글을 작성하세요.",
            model="gemini-1.5-pro"
        )

class EditorAgent(Agent):
    def __init__(self):
        super().__init__(
            name="Editor",
            instruction="당신은 편집장입니다. 작성된 글의 논리적 오류를 잡고 문법을 교정하여 최종본을 완성하세요.",
            model="gemini-1.5-flash"
        )
```

### 3. `main.py` : 워크플로우 구현 및 실행
```python
# main.py
from agent import ResearcherAgent, WriterAgent, EditorAgent
from tools import fetch_market_data, fetch_competitor_data, check_grammar

def run_sequential_workflow(topic):
    print("\n--- 순차적 워크플로우 시작 ---")
    researcher = ResearcherAgent()
    writer = WriterAgent()
    editor = EditorAgent()

    # 1단계: 조사
    raw_data = researcher.run(f"{topic}에 대해 조사해줘", tools=[fetch_market_data])
    
    # 2단계: 작성 (조사 결과가 입력으로 들어감)
    draft = writer.run(f"다음 데이터를 바탕으로 보고서를 작성해: {raw_data}")
    
    # 3단계: 교정 (작성 결과가 입력으로 들어감)
    final_report = editor.run(f"다음 글을 교정해줘: {draft}", tools=[check_grammar])
    
    return final_report

def run_parallel_workflow(topic):
    print("\n--- 병렬적 워크플로우 시작 ---")
    # 각 분야 전문가 생성
    trend_analyst = ResearcherAgent() # 역할을 분리하여 생성 가능
    comp_analyst = ResearcherAgent()
    aggregator = WriterAgent()

    # 병렬 실행 (실제 구현 시 asyncio나 ThreadPoolExecutor 사용)
    # 여기서는 개념적 흐름을 위해 순차적으로 호출하지만, 입력값은 독립적임
    trend_result = trend_analyst.run(f"{topic}의 최신 트렌드를 분석해", tools=[fetch_market_data])
    comp_result = comp_analyst.run(f"{topic}의 경쟁사 현황을 분석해", tools=[fetch_competitor_data])

    # 취합 (Aggregator)
    combined_input = f"트렌드 분석: {trend_result}\n경쟁사 분석: {comp_result}"
    final_report = aggregator.run(f"두 분석 결과를 통합하여 최종 보고서를 만들어줘: {combined_input}")
    
    return final_report

if __name__ == "__main__":
    topic = "생성형 AI B2B 솔루션"
    
    # 순차적 실행 결과
    print(run_sequential_workflow(topic))
    
    # 병렬적 실행 결과
    print(run_parallel_workflow(topic))
```

## 7.5 설계 관점의 분석: 비용 vs 속도 vs 품질 (Trade-off)

멀티 에이전트를 설계할 때 가장 중요한 것은 무조건 많은 에이전트를 쓰는 것이 아니라, 목적에 맞는 구조를 선택하는 것입니다.

| 구분 | 순차적 구조 (Sequential) | 병렬적 구조 (Parallel) |
| :--- | :--- | :--- |
| **품질 (Quality)** | **매우 높음.** 단계별 검증이 가능하며, 앞 단계의 정제된 데이터가 전달됨. | **중간.** 개별 분석은 정교하나, 최종 취합 과정에서 정보 누락 가능성 있음. |
| **속도 (Speed)** | **느림.** 모든 에이전트가 앞 작업이 끝날 때까지 대기해야 함 (Latency 증가). | **빠름.** 여러 작업을 동시에 수행하므로 전체 처리 시간 단축 가능. |
| **비용 (Cost)** | **중간.** 단계별로 필요한 토큰만 사용하며, 불필요한 반복이 적음. | **높음.** 여러 에이전트가 동시에 구동되며, 취합 시 대량의 컨텍스트가 한꺼번에 입력됨. |
| **추천 사례** | 법률 문서 검토, 코드 리뷰, 정밀 보고서 작성 | 뉴스레터 생성, 시장 동향 파악, 다각도 아이디어 브레인스토밍 |

**설계 가이드:**
- **신뢰성이 최우선**이라면? → **순차적 구조** + **검토 에이전트** 추가.
- **응답 시간이 최우선**이라면? → **병렬적 구조** + **경량 모델(Flash)** 배치.
- **복잡도가 매우 높다면?** → 병렬로 데이터를 수집하고, 순차적으로 정제하는 **하이브리드 구조** 설계.

## 7.6 핵심 정리

1.  **멀티 에이전트**는 역할 분담을 통해 단일 에이전트의 프롬프트 복잡도를 낮추고 정확도를 높이는 전략이다.
2.  **순차적 구조**는 `A → B → C` 형태로 흐르며, 예측 가능성과 품질이 높지만 속도가 느리다.
3.  **병렬적 구조**는 `(A, B, C) → Aggregator` 형태로 흐르며, 속도가 빠르지만 비용이 증가하고 취합 로직이 중요하다.
4.  **ADK 2.0**의 그래프 기반 아키텍처는 이러한 결정론적 경로와 AI의 적응형 추론을 결합하여 엔터프라이즈급 워크플로우를 가능하게 한다.

## [정답 및 설계 의도]

**A1. 어그리게이터 (Aggregator)**
- **의도:** 병렬 구조의 핵심 구성 요소인 취합자의 개념을 이해했는지 확인합니다.

**A2. 현재는 그대로 통과됨 / 한계: 단방향 흐름 / 해결: 루프(Loop) 구조 도입**
- **의도:** 순차적 구조의 단방향성(Linearity)을 파악하고, 실제 프로덕션에서는 '재시도'나 '피드백' 루프가 필요함을 인지하게 합니다.

**A3. [병렬 수집/번역] → [순차 요약/체크]**
- **설계 의도:** 5개국 뉴스 수집과 번역은 서로 독립적이므로 **병렬**로 처리하여 속도를 높이고, 요약과 팩트 체크는 앞 단계의 결과가 필수적이므로 **순차**로 처리하는 하이브리드 설계 능력을 평가합니다.

**A4. 단순 수집/번역은 Flash(저비용/고속)로, 최종 취합 및 분석은 Pro(고품질)로 배치하여 전체 비용을 최적화하면서 최종 결과물의 품질을 유지할 수 있음.**
- **의도:** 모델별 특성을 멀티 에이전트 구조에 결합하여 '비용 vs 품질'의 트레이드오프를 최적화하는 설계 관점을 갖게 합니다.

**A5. [설계 가이드]**
- `editor.run()`의 결과값에 "PASS" 또는 "FAIL"이라는 키워드가 포함되게 하고, "FAIL"일 경우 `writer.run()`을 다시 호출하는 루프를 구현해야 함.
- **의도:** 단순 선형 구조를 넘어 적응형(Adaptive) 워크플로우로 확장하는 능력을 배양합니다.
