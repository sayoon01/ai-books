# 9. 미정의 필드 및 예외 데이터 처리 가이드

## 데이터 해석의 경계 설정: 정의되지 않은 필드의 정체

데이터 분석의 완성도는 얼마나 많은 필드를 해석했느냐가 아니라, 해석할 수 없는 필드를 얼마나 명확하게 구분해냈느냐에 따라 결정됩니다. 분석가는 수집된 데이터셋의 모든 컬럼을 어떻게든 의미 있게 해석하려는 경향이 있으나, 근거가 없는 추측에 기반한 해석은 분석 결과 전체를 왜곡시키는 '데이터 오염'의 시작점이 됩니다. 특히 금형 사출 데이터와 같이 물리적 공정과 밀접하게 연관된 데이터에서는 단 하나의 필드 오독이 공정 진단 전체의 오류로 이어질 수 있으므로, '제한적 해석'의 원칙을 철저히 준수해야 합니다.

제공된 필드 설명 자료를 기준으로 볼 때, 다음과 같은 필드들은 설명이 제공되지 않은 '미정의 필드'로 분류됩니다.
*   **중량 관련:** `Weight1`, `Weight2`
*   **품질 및 인적 정보:** `Quality`, `Worker`
*   **식별 정보:** `MoldNo`, `Part No(Injection Machine)`

위 필드들은 자료상에서 설명이 '-'로 표기되어 있으며, 이는 해당 데이터의 측정 시점, 측정 방법, 물리적 단위가 공식적으로 정의되지 않았음을 의미합니다. 분석가는 이러한 필드들을 마주했을 때, 자신의 도메인 지식을 동원해 임의로 정의를 내리는 유혹을 뿌리쳐야 합니다. 예를 들어 `Quality`라는 필드를 보고 당연히 '합격/불합격(Pass/Fail)'을 나타내는 이진 데이터라고 단정 짓고 분석을 진행했다가, 추후 이 필드가 '품질 등급(Grade 1~5)'이나 '불량 코드'를 의미한다는 사실이 밝혀진다면, 해당 필드를 활용해 도출한 모든 통계적 결론은 폐기되어야 합니다.

따라서 분석가는 '자료에 근거한 사실 기반 해석'과 '도메인 지식에 기반한 추론'을 엄격히 구분하여 기록해야 합니다. 사실 기반 해석은 자료에 명시된 수치와 정의를 그대로 옮기는 것이며, 추론은 "필드명으로 보아 ~로 추정된다"라고 명시하는 것입니다. 만약 자료에 설명이 없는 필드를 사실인 것처럼 단정하여 보고서에 작성한다면, 이는 단순한 오기가 아니라 데이터의 신뢰성을 무너뜨리는 치명적인 분석 오류가 됩니다. 정의되지 않은 필드는 '설명 미제공' 상태로 명시하고, 분석 대상에서 제외하거나 정의가 확정될 때까지 보류하는 것이 가장 안전한 분석 전략입니다.

## 미정의 필드의 잠재적 의미와 처리 방법

설명이 제공되지 않았음에도 데이터셋에 필드가 존재한다는 것은, 해당 필드가 시스템적으로는 수집되고 있으나 현재의 분석 목적에서는 우선순위가 낮았거나, 혹은 시스템 로그의 기본 스키마에 포함된 잔재일 가능성이 큽니다. 많은 경우 사출기 제어 시스템이나 MES(제조실행시스템)의 표준 템플릿을 그대로 사용하기 때문에, 실제 현장에서는 사용하지 않지만 데이터베이스 구조상으로는 남아 있는 '더미 필드(Dummy Field)'일 확률이 높습니다. 또는 향후 공정 고도화를 위해 데이터 수집 체계만 먼저 구축해 놓은 확장성 대비용 필드일 수도 있습니다.

그럼에도 불구하고 분석가는 해당 필드들이 잠재적으로 어떤 의미를 가질 수 있는지 추론해 볼 필요는 있습니다. 이는 나중에 현장 전문가에게 질문할 때 구체적인 가이드를 얻기 위함입니다. 필드명을 바탕으로 한 일반적인 추론은 다음과 같습니다.
*   `Weight1`, `Weight2`: 사출된 제품의 실제 측정 중량(Actual Weight)이나, 금형 내의 특정 위치에서 측정된 무게 값으로 추정됩니다.
*   `Quality`: 제품의 검사 결과(합격/불합격) 또는 불량의 유형을 구분하는 코드로 추정됩니다.
*   `Worker`: 해당 Shot을 생산할 당시 설비를 조작한 작업자의 사번이나 이름으로 추정됩니다.
*   `MoldNo`, `Part No(Injection Machine)`: 사용된 금형의 고유 번호나 사출기 관점에서의 파트 식별 번호로 추정됩니다.

중요한 것은 이러한 추론이 실제 데이터와 일치하는지 확인하는 과정입니다. 만약 해당 필드의 값이 모두 비어 있거나, 하이픈(`-`), 혹은 동일한 기본값(Default value)으로만 채워져 있다면, 이는 현재 공정에서 데이터를 수집하고 있지 않다는 물리적 증거가 됩니다. 값이 비어 있는 필드는 분석 단계에서 과감히 제거하여 데이터셋의 크기를 줄이고 연산 효율을 높이는 것이 바람직합니다.

반면, 설명은 없지만 실제 값들이 다양하게 입력되어 있다면, 이는 매우 중요한 정보일 가능성이 큽니다. 이 경우 분석가는 임의로 해석하여 결론을 내리는 대신, "필드명으로 보아 $\text{X}$로 추정되나, 정확한 정의 확인을 위해 현장 담당자의 검토가 필요함"이라는 주석을 달고 보류 상태로 유지해야 합니다. 정의되지 않은 데이터를 억지로 해석에 포함시키는 것보다, 정의되지 않았음을 명시하는 것이 데이터 분석가로서의 전문성과 신뢰도를 높이는 길입니다.

## 예외 데이터의 식별과 필터링 기준

데이터 스키마를 해석하는 것만큼 중요한 것이 바로 '분석 대상에서 제외해야 할 데이터'를 식별하는 것입니다. 모든 수집 데이터가 정상적인 생산 과정을 반영하는 것은 아니며, 공정의 특수성이나 설비의 일시적 중단으로 인해 발생하는 예외 데이터(Outlier)가 섞여 있기 마련입니다. 이를 구분하지 않고 전체 평균이나 상관관계를 분석하면, 실제 공정의 특성이 아닌 '기계적 오류'나 '휴지 시간'이 분석 결과에 반영되는 심각한 왜곡이 발생합니다.

가장 먼저 살펴봐야 할 예외 식별 지표는 `CycleInterval`입니다. 이 필드는 사이클 간의 시간 간격을 나타내는데, 일반적인 사출 공정의 사이클 타임보다 훨씬 긴 수치가 기록된 경우가 있습니다. 특히 자료에서 제시한 **'800초'**라는 기준은 매우 중요한 물리적 구분점입니다. 사이클 타임이 800초를 초과하여 기록되었다면, 이는 제품이 연속적으로 생산된 것이 아니라 작업자가 설비를 잠시 멈춰놓은 '휴지 시간(Idle Time)'으로 해석해야 합니다. 따라서 정상적인 공정 능력을 분석하거나 최적 사이클 타임을 도출할 때는 `CycleInterval > 800`인 데이터를 비정상 사이클로 간주하여 필터링해야 합니다.

다음으로 `Alarms` 필드를 통한 데이터 유효성 검증이 필요합니다. 이 필드는 이진 값(Binary)으로 구성되며, **1은 True(알람 발생), 0은 False(정상)**를 의미합니다. 알람이 발생한 시점(`Alarms = 1`)의 센서 데이터(T, P 값 등)는 설비의 이상 상태나 공정 오류가 반영된 수치입니다. 만약 분석의 목적이 '정상 공정의 최적 조건'을 찾는 것이라면, 알람이 발생한 샷(Shot)의 데이터는 분석 대상에서 완전히 제외하는 것이 원칙입니다. 알람 데이터는 '불량 원인 분석'이라는 별도의 목적이 있을 때만 분리하여 분석해야 하며, 일반적인 상관관계 분석에 포함시켜서는 안 됩니다.

마지막으로 센서 데이터(`T1~T8`, `P1~P8`)의 결측치 처리 원칙입니다. 센서 데이터에서 값이 누락되었거나 0 또는 극단적인 최솟값/최댓값으로 기록된 경우, 이를 단순히 산술 평균으로 채우거나 0으로 간주하는 것은 위험합니다. 금형 내부의 온도와 압력은 물리적 연속성을 가지므로, 특정 시점의 데이터가 누락되었다면 이는 센서의 일시적 통신 오류나 하드웨어 결함일 가능성이 큽니다. 이러한 결측치가 포함된 샷은 물리적 신뢰성이 확보되지 않은 데이터로 판단하여, 해당 샷 전체를 분석 대상에서 제외하는 것이 데이터의 정밀도를 유지하는 방법입니다.

## 데이터 정제(Cleaning)를 위한 최종 체크리스트

모든 필드의 물리적 의미를 해석하고 예외 데이터의 기준을 세웠다면, 이제 수집된 Raw 데이터를 분석 가능한 형태로 정제하는 최종 단계에 진입해야 합니다. 이 과정은 단순한 삭제 작업이 아니라, 앞서 정의한 해석 원칙에 따라 데이터를 분류하는 '결정 트리(Decision Tree)' 과정입니다. 분석가는 데이터를 분석 모델에 투입하기 전, 다음의 체크리스트를 통해 데이터셋의 최종 확정 과정을 거쳐야 합니다.

**1. 필드 분류 및 선택 (Feature Selection)**
*   **해석 가능 필드:** 자료에 근거해 물리적 의미, 측정 시점, 단위가 명확히 정의된 필드 (예: `T_Start`, `P_Max`, `ProcessTime` 등). $\rightarrow$ **분석 유지**
*   **해석 불가능 필드:** 설명이 '-'로 표기되었거나, 추론만 가능할 뿐 근거가 없는 필드 (예: `Weight`, `Quality` 등). $\rightarrow$ **분석 제외 또는 보류**

**2. 데이터 단위 정밀 검증 (Unit Validation)**
*   특히 `ProcessTime1_Fill`부터 `ProcessTime6_Closing`까지의 6단계 시간 데이터가 올바르게 변환되었는지 확인합니다.
*   Raw 데이터의 수치를 **1,000으로 나누어 '초(second)' 단위**로 변환했는지 확인하고, 변환 후의 수치가 물리적으로 타당한 범위(예: 수 초 ~ 수십 초) 내에 있는지 검증합니다. 단위 변환이 누락된 상태로 분석을 진행하면 시간 데이터가 실제보다 1,000배 크게 계산되어 모든 통계치가 왜곡됩니다.

**3. 예외치 필터링 적용 (Outlier Filtering)**
*   `CycleInterval`이 800초를 초과하는 데이터가 제거되었는가?
*   `Alarms` 값이 1인 데이터가 분리되었는가?
*   센서 데이터의 결측치가 포함된 샷이 제거되었는가?

**4. 분석 대상 데이터셋 최종 확정**
*   위의 과정을 거쳐 정제된 데이터셋이 분석의 목적(예: 공정 최적화, 불량 원인 분석 등)에 부합하는지 최종 확인합니다.
*   최종 확정된 데이터셋은 '어떤 기준(800초, Alarms=1 등)으로 필터링 되었으며, 어떤 필드(미정의 필드 등)가 제외되었는지'에 대한 정제 이력을 기록하여 분석 결과의 재현성을 확보합니다.

이와 같은 정제 과정을 거친 데이터만이 비로소 분석의 신뢰도를 담보할 수 있습니다. 모든 데이터를 다 쓰려는 욕심보다, 신뢰할 수 있는 데이터만 남기려는 엄격함이 분석의 성공을 결정짓습니다.

***

**핵심 정리**
*   `Weight`, `Quality`, `Worker` 등 설명이 없는 필드는 임의로 해석하지 말고 '설명 미제공'으로 명시하여 데이터 오염을 방지한다.
*   `CycleInterval` 800초 초과 데이터는 '휴지 시간'으로, `Alarms = 1` 데이터는 '비정상 상태'로 간주하여 분석 대상에서 필터링한다.
*   `ProcessTime`의 6단계 데이터는 반드시 1,000으로 나누어 초 단위로 변환한 후, 정밀 검증 과정을 거쳐 분석에 투입한다.
